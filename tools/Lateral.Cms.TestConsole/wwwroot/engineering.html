Erases every entity, tombstone, ledger row and queued batch so you can start again. It always runs as the admin account, and only works while the CMS has Admin:AllowReset switched on (Development does).

Who can do what

Publishes a fixture entity as the CMS account, then calls every endpoint as every kind of caller and compares each status with what the design says it should be. The wrong-password row runs last because failed sign-ins are throttled per client (a second run within a minute may show 429 there). The admin disable is undone at the end.

What happens to a 10 GB video?

The CMS holds the video. This service only receives the event about it, and the event carries the entity's fields (a title, a description, and a reference to the file), never the file. So the webhook refuses large bodies outright. The file itself goes to the Assets tab: multipart upload, scanning, and ranged downloads. Ingestion queue

The CMS stores a batch, answers 202 and applies it a moment later. This is where it waits. Reading it needs the admin account. A queue that keeps growing, or a batch that has failed, is what an operator watches for.

Failed batches

Set aside after too many failed attempts. They do not hold up the queue; an admin requeues them once the cause is fixed.
